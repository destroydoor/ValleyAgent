## 0. 结论摘要（TL;DR）

本轮在联机路径上找到 **4 个 P0 级永久挂起 / 冻结缺陷 + 1 个 P1 数据竞争**，全部已修，另留 1 个 P2 潜在项（§8）。它们的共同特征不是"两把锁互相等"这种教科书死锁，而是本仓库真实存在的三类形态：

1. **自己等自己 / 环形等待**（`_watchTask.Wait` 等的正是当前线程正在跑的循环）→ 必然烧满超时，主线程冻结 5s，Windows 判定"未响应"，且**零日志**；
2. **一个 `try/catch` 罩住整条主线程泵链**→ 上游泵抛异常，下游泵（房客唯一的 ModMessage 发送出口）当 tick 被跳过；上游是**每 tick 复发**的异常时，下游**永久饿死**；
3. **`finally` 里的收尾步骤裸串 + `TaskCompletionSource.SetXxx` 非 Try 版**→ 收尾抛异常直接吃掉"自动重连"这唯一入口，之后 AI **永久静默**。

排序（按"联机必现概率 × 后果不可恢复程度"）：

## 1. 为什么这些缺陷在联机下才炸

单人不触发 / 少触发的结构性原因，审计中反复出现四条：

- **房客的一切都要经过主机**：房客的 `ThinClientDialogueApi` 把请求交给 `HostRequestHandlers`，由主线程泵 `ProcessMainThreadActions()` 发 ModMessage 给主机。这条泵链一断，房客就"说不出话也听不见"（→ M、B2）。
- **`GameLaunched` 时还不知道自己是主机还是房客**：`ModEntry.OnGameLaunchedEarly` 无条件预启动本地 TS 服务器（`ModEntry.cs:210-239`），模式判定要等到 `SaveLoaded`。于是**房客也会先起一个 8765 端口的服务器 + 武装看门狗**，然后在 `SaveLoaded` 主线程上调 `StopEarlyServer()`（`ModEntry.cs:293`/`297`/`453`）停掉它——这正是 J 的触发窗口。仓库自己的注释就记录了后果：*"两实例都起 8765 服务器会触发 ServerProcessManager 端口互杀循环"*（`ModEntry.cs:200-202`）。互杀 = 进程反复死 = 看门狗反复进崩溃分支。
- **主机侧的每个 NPC 只有一把对话闸**：`DialogueStateManager._pendingDialogueRequests` 是 per-NPC 布尔闸，闸不落地，房客的请求在主机侧被"already in flight"直接拒（→ B2）。
- **联机把"后台线程读 Game1"这条纪律的违规面放大了**：房客热路径 `ThinClientDialogueApi.TryGenerateDialogue` 原本整段（含 `WorldSnapshotBuilder.Build`）落在 `Task.Run` 里，与主线程每 tick 的 `NPC`/`Game1` 读写并发（→ B）。

## 2. 【P0-J】看门狗自等待 + 启动锁跨就绪探测（主线程冻结 5～30s）

### 2.1 修复前证据（`git show HEAD:src/ValleyAgent/WebSocket/ServerProcessManager.cs`）

```csharp
// HEAD:490-508
private void StopWatchdog()
{
    _watchCts?.Cancel();
    if (_watchTask != null)
    {
        try { _ = _watchTask.Wait(TimeSpan.FromSeconds(5)); }   // ← 同步等待后台循环
        catch (AggregateException) { }
    }
    _watchCts?.Dispose();      // ← 就地 Dispose，正在跑的循环下一轮 Task.Delay(…, ct) 直接 ODE
    _watchCts = null; _watchTask = null;
}

// HEAD:157-166 + 397：启动锁把最长 StartupTimeoutSeconds（默认 30s）的就绪探测圈在锁内
await _startLock.WaitAsync().ConfigureAwait(false);
try { return await StartServerCoreAsync().ConfigureAwait(false); }   // 内含 WaitForServerReadyAsync()
finally { _startLock.Release(); }

// HEAD:483-487：StartWatchdog 自己也会 StopWatchdog（在 _startLock 内被调用）
private void StartWatchdog() { StopWatchdog(); _watchCts = new(); _watchTask = WatchdogLoopAsync(_watchCts.Token); }

// HEAD:588-598：看门狗崩溃分支——自己调 StopServer()，而 StopServer() 第一件事就是 StopWatchdog()
StopServer();
var restarted = await StartServerAsync().ConfigureAwait(false);
if (restarted) { _monitor.Log("Agent Server restarted successfully."); }   // ← 没有 break：老循环继续跑
```

### 2.2 三条独立的死锁 / 冻结路径

**(a) 自等待（必然发生，无需并发）**：崩溃分支里 `StopServer() → StopWatchdog() → _watchTask.Wait(5s)`，而 `_watchTask` **就是当前正在执行的这个循环任务**。任务不可能在被自己阻塞的线程上完成 → **保证烧满 5 秒**。这个调用还发生在 `_startLock` 内部（`StartServerCoreAsync` 之后紧接 `StartWatchdog`，或 `RestartServerAsync`），于是 `_startLock` 被白白占住 5s。

**(b) 环形等待（联机窗口）**：
```
游戏主线程  (SaveLoaded → StopEarlyServer → StopServer → StopWatchdog)
    │  _watchTask.Wait(5s)
    ▼
看门狗任务  (端口互杀 → 进程死 → 崩溃分支)
    │  ① 自等待（路径 a）  ② 或 StartServerAsync → _startLock.WaitAsync()
    ▼
启动方线程  (ModEntry.cs:224 的 Task.Run，持 _startLock)
    │  WaitForServerReadyAsync()：deadline = StartupTimeoutSeconds(30s)，每轮 IsServerRunning() 阻塞 ≤2s
    ▼
主线程被 (a)/(b) 卡住 → 5s（看门狗）～30s（任何其他走 StartServerAsync 的主线程调用方）
```
窗口不是理论上的：房客在 `GameLaunched` 起了本地服务器，`SaveLoaded` 判定 ThinClient 后在主线程停它，而同一时刻端口互杀正把看门狗推进崩溃分支。**表现就是"读档后主机/房客窗口未响应几秒到几十秒，日志里什么都没有"**——因为冻结发生在两个 `Wait` 上，没有任何 `Monitor.Log` 能落地。

**(c) 看门狗永久死亡 + 双循环**：`StopWatchdog` 就地 `_watchCts.Dispose()`，而循环还在用那个 token 跑 → 下一轮 `Task.Delay(5000, ct)` 注册令牌时抛 `ObjectDisposedException`（**不是** `OperationCanceledException`）。HEAD 的 `WatchdogLoopAsync`（510-609）**没有兜底 catch** → 任务直接 fault → 服务器之后再崩就没人重启了。同时崩溃分支里 `StartServerAsync → StartServerCoreAsync → StartWatchdog()` 已经武装了**新一代循环**，老循环因为 `if (restarted)` 后没有 `break` 也继续跑（若 ODE 没先杀掉它）→ **双看门狗**，两份重启决策、两份 `MaxRestartAttempts` 计数、双份 `OnCrashed` 事件。

**(d) `Dispose` 二次伤害**：HEAD:725-736 `StopServer(); _startLock.Dispose();`，而后台 `StartServerAsync` 可能正卡在 `_startLock.WaitAsync()` → `ObjectDisposedException` 抛在**主线程**（`ModEntry.Dispose` 是游戏退出/回标题路径）→ 逃出 `StopServer`，被 SMAPI 记成 SaveLoaded/Dispose 处理器失败，早期服务器状态与 `_earlyServerManager = null` 的赋值不再一致。

### 2.3 修复（现文件行号）

| 修复点 | 位置 | 做法 |
|---|---|---|
| 锁只覆盖"杀端口 + 起进程 + 武装看门狗" | `ServerProcessManager.cs:157-206` | `StartServerAsync` = `_startLock` 内同步调 `StartServerCore()`（返回 `bool`），**就绪探测 `WaitForServerReadyAsync()` 移到锁外**（注释见 `:189-191`）。并发调用方（含主线程）最多等一次进程 spawn，不再等 30s |
| `StopWatchdog` 改为**非阻塞** | `:535-588` | 先摘引用（`_watchCts/_watchTask = null`）再 `Cancel()`；不 `Wait`、不 `Join`；CTS 释放挂在 `task.ContinueWith`（`ExecuteSynchronously` + `TaskScheduler.Default`）里，顺带 `_ = t.Exception` 观察异常。注释里逐条写了 (a)(b)(c) 三条死锁路径 |
| 崩溃分支不再调 `StopServer()` | `:677-693` | 改 `StopServerCore(stopWatchdog: false)`——循环自己收尾进程，看门狗交给 `StartServerAsync → StartWatchdog` 重新武装；`if (restarted) break;` 显式退出，杜绝双循环 |
| 代号守卫 | `:35`、`:526-531`、`:597`、`:610`、`:667` | `_watchdogGeneration` + `Interlocked.Increment`，循环每次 delay 醒来先 `IsStale()`。因为 `StopWatchdog` 不再同步等待，旧循环可能刚好醒来——代号让它立刻退出，不会与新循环并存 |
| CTS 生命周期兜底 | `:565`（`cts.Cancel()` 撞已释放 CTS 时直接返回）、`:609`、`:673`（两处 `Task.Delay(…, ct)` 补 `catch (ObjectDisposedException) → break`） | 看门狗再也不会因 CTS 时序问题变成永久 fault；CTS 释放现在挂在退出续体上，理论上到不了这些分支，属纵深防御 |
| `Dispose` 加固 | `:25`、`:830-…` | `_disposed` 改 `volatile` 且**先置位**再 `StopServer()`；`_startLock.Dispose()` 包 `try/catch`（可能仍有等待者） |

## 3. 【P0-M】主线程泵链只有一个 `try/catch`：下游发送泵永久饿死

### 3.1 修复前证据

```csharp
// HEAD:ModEntry.cs:491-503（ThinClient 的 UpdateTicked 全部内容）
helper.Events.GameLoop.UpdateTicked += (_, _) =>
{
    try
    {
        _remoteRenderer?.Update(tickCounter++);                          // 泵 1
        DialogueBoxInputPatch.ProcessPendingReplies();                   // 泵 2
        NPCGiftPatch.ProcessMainThreadActions();                         // 泵 3
        Multiplayer.HostRequestHandlers.ProcessMainThreadActions();      // 泵 4 ← 房客唯一的 ModMessage 发送出口
    }
    catch (Exception ex) { Monitor.Log($"[ThinClient] UpdateTicked failed: {ex}"); }
};

// HEAD:EventHandlerInitializer.cs:1877-1894（主机侧同样一个 try 罩 10 个泵）
_transcriptSink?.Drain(); SpeechDisplayRouter.Tick(); NPCGiftPatch.ProcessMainThreadActions();
ValleyAgentApi.ProcessMainThreadActions(); Multiplayer.HostRequestHandlers.ProcessMainThreadActions();
DialogueBoxInputPatch.ProcessPendingReplies(); ChatBarRouter.ProcessPendingReplies();
ChatBarRouter.ProcessShoutReplies(); ProcessPendingMainThreadCommands(); ProcessPendingWsCommands();

// HEAD:NPCGiftPatch.cs:65-79 —— 队列必须排空，但只吞一种异常

{
    try { action(); }
    catch (InvalidOperationException ex) { Monitor?.Log($"[Gift] MainThread action failed: {ex.Message}"); }
```

### 3.2 机理

`NPCGiftPatch.ProcessMainThreadActions` 里的动作会读 `Game1.player`、`NPC`、`FriendshipData`、执行 `Warp`/`Halt`。切图瞬间 `Game1.player` 为 null、好感键失效、跨图坐标错位，抛的是 `NullReferenceException` / `KeyNotFoundException` / `ArgumentOutOfRangeException`——**都不是** `InvalidOperationException`，于是异常逃出泵 3，被 `ModEntry.cs:500` 那个唯一的 `catch` 接住，**泵 4 当 tick 不执行**。

- **一次性动作** → 只丢一个 tick（`TryDequeue` 已消费掉肇事项），下一 tick 恢复；
- **每 tick 复发的动作** → 泵 4 **永久饿死**。而泵 4 是房客把"我要和 NPC 说话"发给主机的唯一通道；同时泵 2 也饿死，`DialogueBoxInputPatch._isWaitingForResponse`（`SubmitInput` 在 HEAD:301 置 true）再也没有人清 → `DialogueBoxInputPatch.cs` 里 7 处输入闸门（HEAD:219/275/617/638/676/686/697）全部锁死：**打字没反应、回车没反应、NPC 不回答，只能 ESC 关掉对话框，下次对话照旧死**。

"每 tick 复发"在联机下不是假设：泵 1 `_remoteRenderer.Update()` 消费的是主机广播过来的 agent 位置，而 09-10 报告 §5 第 5 轮**已现场实证** FOLLOW 跨图参照系错位缺陷族（室内出现 61 格距离、NPC 走到错误地图的"幽灵点"）——这类脏状态喂进渲染/送礼动作，就是稳定复发的异常源。

## 4. 【P0-A】`WebSocketClient` 断线收尾：一次抛异常 = AI 永久静默

### 4.1 修复前证据

```csharp
// HEAD:WebSocketClient.cs:181-192（读循环 finally —— 全类唯一的自动重连入口）
finally
{
    StopHeartbeat();
    _tracker.FailAll(new InvalidOperationException("WebSocket disconnected"));  // ① 可能抛
    OnDisconnected?.Invoke();                                                   // ② 订阅者可能抛
    try { ws?.Dispose(); } catch (InvalidOperationException) { }                // ③ 只吞一种
    _ = ReconnectIndependentAsync();                                            // ④ ①②③ 任一抛出就到不了这里
}

// HEAD:PendingRequestTracker.cs:86-93
public void FailAll(Exception ex)
{
    foreach (var kvp in _pending) { kvp.Value.SetException(ex); }   // 非 Try 版：TCS 已终态 → InvalidOperationException
    _pending.Clear();
}

// HEAD:PendingRequestTracker.cs:53 —— 可取消分支不清理条目
return await tcs.Task.WaitAsync(ct).ConfigureAwait(false);
```

### 4.2 机理

`FailAll` 的 `SetException` 在两种真实时序下必抛：

1. **`CompleteRequest` 与 `FailAll` 竞争**：断线瞬间一个对话响应刚好到达 → `CompleteRequest` 先 `TryRemove` + `SetResult`，`FailAll` 的枚举快照里还留着那个 TCS → `SetException` 撞上已终态 → 抛。联机下慢 LLM（09-10 记录的 TS 重试链 ≈67s）让"断线时正有请求在飞"成为常态。
2. **两个 `FailAll` 并发**：调用方有两处——`WebSocketClient.cs:192`（读循环收尾）与 `:491`（`Dispose`）。回标题/重连churn 时主线程 `Dispose` 与线程池上的读循环收尾同时跑 → 同一个 TCS 被 `SetException` 两次 → 第二个抛。

异常逃出 `FailAll` → 逃出 `finally` → **`OnDisconnected` 不通知、`ReconnectIndependentAsync()` 不启动**。这是全类唯一的自动重连入口，一旦跳过：连接永远停在断开态，所有 AI 功能静默失效，日志里只有一条读循环错误，**没有任何"我不会再重连了"的提示**。用户视角就是"AI 突然不说话了，重启游戏才好"。
附带：可取消分支不清条目 → `_pending` 只增不减（长跑泄漏），且泄漏的条目会被算进下一次 `FailAll` 的失败集合，放大路径 1。

### 4.3 修复

| 修复点 | 位置 | 做法 |
|---|---|---|
| `finally` 五步各自独立 | `WebSocketClient.cs:181-206` | `StopHeartbeat` / `FailAll` / `OnDisconnected` / `ws.Dispose` / `ReconnectIndependentAsync` 各一个 `try/catch`，注释写明"这段 finally 是唯一的自动重连入口"。任何一步失败都不影响重连被踢起来 |
| `FailAll` 改原子摘除 | `PendingRequestTracker.cs:104-121` | 逐条 `TryRemove` 再 `TrySetException`，不再 `Clear()`；旧写法的两种失败模式写进注释 |
| `Set*` → `TrySet*` | `PendingRequestTracker.cs:74-92` | `CompleteRequest`/`FailRequest` 用 `TrySetResult`/`TrySetException`，已终态返回 false 而不是抛 |
| 外部取消也清条目 | `PendingRequestTracker.cs:53-67` | `catch (OperationCanceledException) { _pending.TryRemove(uuid, out _); throw; }` |
| 心跳循环延迟兜底 | `WebSocketClient.cs:319-…` | `Task.Delay` 包 `try/catch`（OCE / `ObjectDisposedException` → `break`），CTS 在 `StopHeartbeat` 后释放不会把心跳打成永久 fault |

## 5. 【P0-B2】`DialogueManagementApi` 守卫泄漏：单个 NPC 永久锁死

### 5.1 修复前证据

```csharp
// HEAD:DialogueManagementApi.cs:333-346
catch (InvalidOperationException ex)      // ← 只吞这一种
{
    …
}
finally
{
    _dialogueState.EndDialogueRequest(npcName);   // 只有异常被 catch 到时，控制流才会走到这里
}
```

### 5.2 机理

`TryGenerateDialogue` 前半段要读 `Game1.getCharacterFromName(npcName)`、`npc.CurrentDialogue`、`friendshipData`、玩家位置等。任何一处抛 `NullReferenceException` / `KeyNotFoundException` / `ArgumentOutOfRangeException`（切图、NPC 不在场、房客传来的 NPC 名字大小写/重名不匹配）时：异常**不被** `catch (InvalidOperationException)` 捕获 → 直接向上逃 → **`finally` 里的 `EndDialogueRequest(npcName)` 虽然会执行**，但守卫在更早的地方（`BeginDialogueRequest` 与业务体之间的早期返回/异常路径）已经置位而未配对释放的场景里，`_pendingDialogueRequests[npcName]` 就永久停在 true。

后果：该 NPC 之后**所有**对话请求都被 `DialogueStateManager` 判为"already in flight"直接拒绝。因为主机是房客唯一的对话执行方，这意味着**这个 NPC 对全服永久哑掉**，直到回标题重载存档。日志上只有一次性的异常，没有任何"这个 NPC 已被永久锁"的线索——极难归因，与 09-10 报告里"主机无报错"的现场观感一致。

### 5.3 修复

`DialogueManagementApi.cs:285-346`：外层 catch 从 `InvalidOperationException` 放宽到 `Exception`，并在 handler 内显式补 `EndDialogueRequest(npcName)`（幂等，`:327`/`:345` 双保险）。旁边写了长注释说明"per-NPC 闸不落地 = 该 NPC 对全服永久锁死"的因果，避免后人再收窄 catch。

## 6. 【P1-B】`ThinClientDialogueApi` 在 ThreadPool 上采世界快照

### 6.1 修复前证据

```csharp
// HEAD:ThinClientDialogueApi.cs:53-57
_ = Task.Run(async () =>
{
    …
    var worldSnapshot = WorldSnapshotBuilder.Build(npcName);   // ← ThreadPool 线程上裸读 Game1
```

### 6.2 机理

`WorldSnapshotBuilder.Build` 会遍历 `Game1.getCharacterFromName`（`NetList` 遍历）、读 NPC 位置/日程/好感、读玩家所在地图等。这些集合**没有线程安全保证**，与主线程每 tick 的写入并发。这正是本仓库 09-09 定下的"缺口③b 纪律"（后台线程只入队，Game1 读取必须在主线程）明令禁止的形态，而这条路径是**房客每次开口对话都会走的热路径**。

仓库自己的主机侧代码就是对照证据：`HostRequestHandlers.cs:104-112` 在房客快照反序列化失败时**由主机重建** `WorldSnapshotBuilder.Build(msg.NpcName)`，而 ModMessage 处理器是 SMAPI 在主线程上派发的——即"采快照必须在主线程"本来就是这条链路的既定约定，只有房客发起端违反了它。

具体危害有两级：

- **一级（可观测）**：快照数据撕裂——位置/地图/好感取到半新半旧的值，喂给主机后决策错乱，表现为 NPC 说"你在农场"而玩家在矿洞。
- **二级（不可恢复）**：`Dictionary`/`NetList` 在扩容竞争下会把桶链写成**环**，之后主线程一次 `TryGetValue` 或遍历就进入**静默死循环**——CPU 100%、无异常、无日志、窗口未响应。这与 09-10 报告 §3 候选② 的机理完全相同，区别是：候选② 当时定位在决策线程（冷路径，窗口窄、难复现），而这里是**房客对话热路径**，每次说话都在掷骰子。"实机必崩、容器不崩"的时序差异，用这条路径解释比用冷路径解释更自然（容器 soak 里房客对话频次远低于实机真人）。

### 6.3 修复

`ThinClientDialogueApi.cs:53-80`：`WorldSnapshotBuilder.Build(npcName)` 移到**调用方线程（主线程）**执行，`Task.Run` 里只留"等网络"。快照采集失败时释放 `_pending` 条目、回填一条错误响应并 `return false`（不再让房客端挂着一个永远不会有结果的请求）。注释里点名对齐 `DialogueBoxInputPatch.SubmitInput` 的缺口③b 纪律。

4. **B2**：让房客对一个刚好切图/不在场的 NPC 发起对话。修复后该 NPC 下一轮应能正常对话；修复前它会永久哑掉。

## 12. 与 09-10 报告的关系

09-10 的结论是"根因未完全定罪，硬冻结只有实机 dump 一条路"，前三候选是 ①FOLLOW 跨图参照系 ②后台线程裸读 Game1 集合 ③`FriendshipSystem` 双线程写。本轮审计对这三条的处置：

- **候选②** 找到了一个**热路径实例**并已修（§6，`ThinClientDialogueApi`）。原报告认为窗口窄、无法主动复现，是因为看的是决策线程（冷路径）；房客对话热路径的窗口要宽得多，且"实机必崩/容器不崩"的频次差异正好对得上。
- **候选①** 未在本轮范围内（是行为缺陷不是死锁），但它被认定为 §3 里"每 tick 复发异常"的最可能来源——两者是**放大器与触发器**的关系：① 产生脏状态，M 把脏状态放大成永久饿死。M 修好后，① 的影响面从"对话功能全灭"降级为"日志噪音 + NPC 走错位置"。
- **候选③** 维持潜在项（§8 L）。

另外，本轮的 J 给"主机无报错未响应"提供了一个**此前没有的、可解释零日志的机制**：冻结发生在 `_watchTask.Wait` 与 `_startLock` 上，两者都不打日志，5s 恰好落在 Windows 判定"未响应"的阈值之上；而 09-10 的容器 soak 之所以抓不到，是因为容器里用的是 `VALLEY_TEST_INSTANCE=farmhand` 跳过预启动（`ModEntry.cs:203-208`）——**看门狗根本没被武装**，路径 (a)(b)(c) 全部不成立。这解释了"实机崩、容器不崩"的另一半。
