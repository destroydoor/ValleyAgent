## Phase 0 — 架构债务收尾（先行，全是接线活，解锁后续一切）

### E0-1 消费 friendshipDelta + 删除 friendship_eval 死管道
- **背景**：TS 端已落地（`DialogueResponse.friendshipDelta/friendshipReason`、evaluate_friendship 工具、delta=0 不携带）。C# 端未动。
- **改动**：
  1. C# dialogue_response 处理处读取 `friendshipDelta`，交给 FriendshipSystem 应用变动并写友谊历史。
  2. 删除发送端：`WebSocketClient.cs:63`（发 `friendship_eval`）与 `FriendshipSystem.cs:122`（`EvaluateFriendshipAsync`）整条调用链。
- **验收**：`check:protocol` DEAD_PIPELINES 8→7；一次对话后好感度变化出现在日志与存档。

### E0-2 海莉修复：set_state 接线 + action_result 回执
- **背景**：根因在 `DialogueBoxInputPatch.cs:384-404`——`TrySetAgentState` 返回值被丢弃且 `continue` 跳过反馈，导致 NPC 以为跟随了实际没有。
- **改动**：成功/失败都向 TS 发 `action_result`（含 `reason`，复用已有 REASON_CN 管道）；失败时 TS 侧记忆与现实保持一致。
- **验收**：复现海莉场景——对话要求跟随 → NPC 实际进入 FOLLOW；若被状态机拒绝，NPC 下一轮对话能说出"我跟不上/我过不去"而非以为自己跟着。

### E0-3 state_changed 消息两端落地
- **改动**：C# 在状态机转换成功后发 `state_changed {npcName, from, to, reason}`；TS `protocol-adapter` routeMessage 新增 case，更新 NPC 状态镜像供 prompt 使用。
- **验收**：每次状态转换在日志可见；对话时 NPC 对自身当前状态的认知与实际一致。

### E0-4 消息分级落地（删切图播报 + 灰色系统消息）
- **依据**：【需求】§3.7。
- **改动**：
  1. 删除跨图跟随旅行的所有播报（"我马上来"/"我到了"类发言点，实施时 grep 定位，预计涉及 AgentNavigator / TalkHandler / 旅行相关 speech 调用）。
  2. 新增灰色系统消息（灰色斜体或灰色普通字，与 NPC 彩色发言明确区分）：Agent 模式退出 `*XXX离开了*`；跨图跟丢 `*XXX没跟上*`。
  3. AI 主动决定离开仍走 speak 人设发言，不得降级为系统消息。
- **验收**：跟随状态连续切 5 张图，聊天栏零消息；交还原版日程出现灰色离开消息；跟丢有灰色提示。

### E0-5 REASON_CN 未知枚举中文兜底
- **改动**：`stardew-agent.ts:73` 的 `?? r.reason` 改为中文兜底（如"未知原因"），防止未来 C# 新增枚举值时 prompt 混入英文。
- **验收**：bun test 全绿；注入未知 reason 的单测渲染为中文。

### E0-6 NPC 认知对齐（位置/钱包/背包注入）
- **背景**：2026-08-04 实测暴露四问题中的三个——NPC 幻觉去过矿洞（worldSnapshot 的 location 是玩家地图、set_state 意图记忆被当事实）、不知自己钱包余额、不知自己背包内容（worldSnapshot.inventory 实为玩家背包，被 TS 误当 NPC 的）。违反设计哲学第 8 条。
- **改动**：
  1. worldSnapshot 增加 `npcLocation`/`npcMoney`/`npcInventory`（C# record + WorldSnapshotBuilder 填充，TS types + decoder）。
  2. TS prompt 当前场景段：位置锚定改用 npcLocation（缺失回退玩家地图），新增"你的钱包/你的背包"两行（缺数据显示"（未知）"）。
  3. `set_state` 记忆措辞意图化（"（意图）我打算进入 X 状态…"）；`get_info inventory`/`give_item`/`give_gift` 改用 NPC 真背包。
- **验收**：复现海莉场景——NPC 能正确说出自己在哪、有多少钱、包里有什么；未去过矿洞时不声称去过。

- **依据**：【记忆】TranscriptStore 设计；AGENTS.md 设计哲学第 7 条。
- **改动**：TS 侧落盘——NPC 决策输入上下文与输出、对话全文、导演编排思考、工具调用与回执；C# 侧落盘——命令执行结果、状态转换、钱包/背包变动（为 Phase 3 预留）。

## Phase 2 — 体验快赢（小改动、直接提升手感）

### E2-1 动态速度
- **依据**：【需求】§4。
- **改动**：跟随/行动按距离分段调速（默认 >8 格 2×、3–8 格 1.5×、<3 格 1×，进配置），动画帧率等比例缩放。接线点：MovementService / PathFindController 速度参数与 NPC 动画帧率。**不做体力惩罚。**
- **验收**：跟随中拉开距离 NPC 明显加速追赶，近处并肩行走；动画无滑步感。

### E2-2 聊天栏玩家→NPC + 路由消歧 + 会话模式
- **依据**：【需求】§3.1、§3.1.1。
- **改动**：聊天栏输入拦截；四层路由优先级（名字提及 → 当前会话 → 跟随/雇佣者 → 最近交互+距离）；沉默权；会话模式（60 秒超时，会话内不计主动额度）。
- **验收**：【需求】§3.6 验收标准全部通过；多 NPC 在场时路由正确、不抢话。

### E2-3 长文本规则
- **依据**：【需求】§3.3。
- **改动**：≤1 句可气泡；>1 句不进气泡、进聊天栏按句分段间隔弹出（间隔可配置）。
- **验收**：三句话回复按句间隔出现在聊天栏，头顶无气泡。

## Phase 3 — NPC 经济系统（最大的一块，依赖 Phase 0 的反馈管道）

### E3-1 数据层：钱包 + 背包
- **依据**：【需求】§1.1；数据全在 C#（已拍板）。
- **改动**：AgentInventory 扩展钱包字段；逐 NPC 初始资金/物品表（数据文件）；存档持久化；变动写 TranscriptStore。
- **验收**：存档/读档后钱包背包一致；每次变动有日志。

### E3-2 定价引擎
- **依据**：【需求】§1.2、§1.3、§1.4。
- **改动**：公道价 = 游戏数据卖价；逐 NPC 精明度浮动率表；购买力约束（出价上限 = min(心理价, 钱包 × 预算比例)，预算比例谨慎 0.3/普通 0.5/豪爽 0.8）；阶梯还价（最多 3 轮、让步逐轮减半、恶意低价警觉）。
- **设计倾向（待确认）**：数值判定（区间、购买力、阶梯步进）放 C# 规则侧，LLM 只做话术——LLM 断线时交易可降级不卡死。实施前与【需求】§7 开放问题 4 一并拍板。
- **验收**：【需求】§1.9 验收标准（防坑、购买力、三人三反应、第 4 轮必拒、连崩两次关闭）。

### E3-3 交易流程：右键菜单 + pending offer + 原子成交
- **依据**：【需求】§1.8。
- **改动**：持物品右键 Agent NPC 出"送礼/交易/取消"菜单（非 Agent 村民保持原版）；pending offer（每 NPC 限 1 个，30 秒/走远/切图作废 + NPC 吐槽）；C# 成交原子校验（物品在/数量够/双方钱够），失败回 action_result.reason。
- **验收**：谈妥后丢弃物品再确认 → 成交失败且 NPC 知情；超时作废有提示。

### E3-4 只读背包展示界面
- **依据**：【需求】§1.8。
- **改动**：复用箱子/背包界面做只读展示（能看、能点选进入谈价、不能拖走）；预留"展示模式"抽象供未来偷窃功能复用。
- **验收**：无法从界面直接拿走任何物品；点选物品正确进入还价流程。

### E3-5 NPC 求购
- **依据**：【需求】§1.5。
- **改动**：逐人设求购生成（格斯收食材、克林特收矿石等），求购价 1.0~1.1× 公道价可配置；经聊天栏/对话发布；频率受限。
- **验收**：求购出现频率合理不刷屏；交付成交后 NPC 钱包正确扣减。

## Phase 4 — 雇佣系统（依赖 Phase 3 的钱包与还价）

### E4-1 契约 + 计价 + 朋友价
- **依据**：【需求】§2。
- **改动**：契约模型（任务类型/期限/报酬）；计价 = 人设日薪基准 × 危险系数 × 缺钱修正 × 好感修正；还价复用 E3-2 阶梯；朋友价/免费 + "长工"频率保护（一周免费 ≥3 次触发吐槽）；雇佣期为导演高优先级 beat，违约抗议与中止。
- **验收**：【需求】§2.6 验收标准（缺钱/有钱反应不同、契约优先、长工保护、违约有代价）。

### E4-2 玩家→NPC 支付执行
- **背景**：2026-08-04 实测：玩家对话中说"付你 500"，NPC 答应了但钱没到账——玩家→NPC 方向支付链路不存在（TradeSettlement 只有 NPC 买玩家物品方向；AddMoney 生产调用点只有交易结算和初始资金）。
- **改动**：
  1. TS 新增 `receive_payment` 工具（两阶段，仿 give_gift C1 模式：execute 只写意图，action_result 落地记忆）。
  2. C# `TradeSettlement.SettlePlayerPays`：预校验玩家余额 → 玩家扣款 → NPC AddMoney，失败回 reason（payer_wallet_insufficient）。
  3. CommandExecutor 处理 receive_payment action，成功发聊天栏灰色系统消息 `*你付给{npc} {amount}g*`（§3.7 系统消息样式），结果走 callId action_result 反馈环。
- **验收**：对话中 NPC 答应收款后玩家钱包 -N、NPC 钱包 +N、聊天栏灰色到账提示、NPC 下轮对话记得收到了钱；玩家钱不够时 NPC 知情。契约到期自动结算工资（ContractService.Complete 接线）属 E4-1 收尾，不在本条目。

## Phase 5 — 喊话频道 + 主动发言（依赖 Phase 2 的路由与会话模式）

### E5-1 作息表数据
- **依据**：【需求】§3.4；开放问题 7。
- **改动**：逐 NPC 起床时间表（优先从原版 schedule 数据提取，不足则数据文件补）。
- **验收**：任意时刻可查询 NPC 是否已醒。

### E5-2 晨间喊话
- **依据**：【需求】§3.4。
- **改动**：喊话识别；确定性路由优先、LLM 只做歧义兜底（最多 1 次调用）；时段×人设×关系回应（未醒/在忙可不回）；几秒延迟回应；连续清晨骚扰写记忆并升级回应；被动回应不占主动额度。
- **验收**：【需求】§3.4 验收标准全部通过。

### E5-3 主动发言
- **依据**：【需求】§3.2。
- **改动**：话痨度逐人设参数；场景事件触发 + 硬冷却；默认每人每日 ≤2 条可配置；会话模式豁免。
- **验收**：上限生效；无触发不刷屏；触发时机贴切。

## 测试策略（每 Phase 通用）

按【测试】五层执行：L1 契约（check:protocol 随 Phase 0 逐项转绿）→ L2 组件（TS 单测先行，bun test 必须全绿）→ L3 故障注入（每个新流程至少一条：LLM 断线、成交时物品消失、切图中跟丢）→ L4 不变量（钱包不为负、背包物品数守恒、pending offer 唯一）→ L5 体验打分（对照【需求】各章验收标准）。

## 全局红线

- TS 只做智能，C# 只做执行与数据；数值判定优先落 C# 规则侧，LLM 出话术。
- 一切 AI 行为全量留痕（Phase 1 之后不得再出现"日志里看不到为什么"）。
- 每次状态/资产变动必须有回执，NPC 对现实的认知不得与游戏状态脱节（海莉事件是总教训）。
- bun test / tsc / check:protocol 全绿才允许进入下一 Phase。
