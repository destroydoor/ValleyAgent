## 1. 已落地：Track A — L1 协议契约测试（架构地基）

### 1.1 为什么这是第一优先级

设计文档测试篇 §1 指出三个根因：没有契约层、没有故障注入、没有不变量。**契约层是其余两者的前提**——没有单一事实源，故障注入和不变量都无从对齐。设计文档原文："这一条如果今天存在，`decision`/`friendship_eval` 死管道在提交当天就会红。"

### 1.2 交付物

- **`<VALLEYAI_ROOT>\protocol\messages.json`**：wire 协议单一事实源，21 个消息类型（15 实证 + 6 planned）。每条含 `type`/`direction`/`transport`/`status`/`routed_by_ts`/`sent_by_csharp`/`description`/`fields`。
- **`<VALLEYAI_ROOT>\scripts\check-protocol-contract.ts`**：静态交叉检查脚本，`bun run scripts/check-protocol-contract.ts` 运行。
- **`<VALLEYAI_ROOT>\package.json`**：注册 `"check:protocol"` 脚本。

### 1.3 检查逻辑（三档）

1. **DEAD_PIPELINES（exit 1）**：`S_send - S_route`，C# 发送但 TS 不路由。当前 8 个：`decision`/`friendship_eval`/`gift_eval`/`rag_query`/`state_sync`/`consolidate_day`/`emotion_sync`/`memory_sync`。
2. **ORPHAN_ROUTES（警告）**：`S_route - S_send`，TS 路由但 C# 从不发。当前 1 个：`tool_call_result`（C# 用 `action_result` 而非 `tool_call_result`，命名不一致，待统一）。
3. **SCHEMA_DRIFT（exit 1）**：`messages.json` 声明的 status 与代码实证不一致。当前 0 个（schema 与代码一致）。

### 1.4 C# type 提取的 5 种模式（脚本实现要点）

`SendRequestAsync("decision", ...)` 字面量第一参数 / `SendTestMessageAsync(ProtocolV2.MessageTypeStateSync, ...)` 常量第一参数 / `new { type = "consolidate_day" }` 匿名对象字面量 / 匿名对象常量 / `new ProtocolV2.StateSyncMessage()` 消息类默认 Type。脚本解析 `ProtocolV2.cs` 建立常量名→字符串值、类名→默认 type 的映射。XML doc 注释用后行断言排除，避免误匹配。

### 1.5 "第一天就红"的价值

脚本 exit 1 不是失败，是**预期状态**。红色的死管道清单就是待修复 backlog。当后续 track 把死管道接回或删除时，脚本逐步转绿，成为完成的客观判据。这是防止"休眠代码腐化"（长期篇 §4.6）的守门人。

### 2.4 为什么没改 DialogueBoxInputPatch.cs:384-404（海莉事件直接根因）

这是**本次会话最重要的延后决策**，必须说清。

`DialogueBoxInputPatch.DispatchDialogueActions` 的 set_state 分支（`:384-404`）是海莉事件的直接根因：
- `:395` `_ = api.TrySetAgentState(npc.Name, stateStr);` 丢弃返回值
- `:398-401` 即使状态机拒绝，`UpdatePreDialogueState` 仍按 LLM 想要的字符串更新 preState
- `:403` `continue` 跳过 `CommandExecutor.ExecuteAction` → 不发 action_result

**没改的原因**：这个分支调用 `ValleyAgentApi.TrySetAgentState`，后者驱动真实的状态机转换（`AgentStateMachine.ForceTransition`）。修复需要验证：
1. 状态机拒绝时（agent 未分配/非法状态/BLOCKED）`TrySetAgentState` 返回 false 的真实路径
2. 改成不 `continue`、走 `CommandExecutor.ExecuteAction` 后，set_state 是否会重复执行（CommandExecutor 的 ExecuteSetState 是桩，真切换在 API 层）
3. preState 恢复逻辑（`NPCDialoguePatch.UpdatePreDialogueState`）在状态机拒绝时该用什么值

这些都需要**启动游戏 + 触发对话 + 观察状态机**才能验证，不符合本次"纯静态可验证"边界。强行改会引入不可测的行为漂移，违反铁律 #3。

**具体改法（延后到下次会话，需游戏运行验证）**：

```csharp
// DialogueBoxInputPatch.cs:384-404 改法
if (tool.Equals("set_state", StringComparison.OrdinalIgnoreCase) && isAgent && _agentService != null)
{
    var stateStr = action.Args != null
        && action.Args.TryGetValue("state", out var stateObj)
            ? stateObj?.ToString()
            : null;
    if (!string.IsNullOrEmpty(stateStr))
    {
        var api = new ValleyAgentApi(_agentService, _agentService.AllocationManager);
        bool ok = api.TrySetAgentState(npc.Name, stateStr);  // 不丢弃返回值
        if (ok && Enum.TryParse<AgentState>(stateStr, true, out var newState))
        {
            NPCDialoguePatch.UpdatePreDialogueState(npc.Name, newState);  // 仅成功才更新
        }
        // 关键：不发 continue，让动作进入 CommandExecutor.ExecuteAction 回发 action_result
        // 但 CommandExecutor.ExecuteSetState 是桩，需先让它调 api.TrySetAgentState 并返回结果
        // 或在此分支直接构造 action_result 回发，跳过 CommandExecutor
    }
    // 移除 continue; —— 改为 break 或 fall-through 取决于是否要让 CommandExecutor 介入
}
```

配套需要：
1. `CommandExecutor.ExecuteSetState` 从桩改成真正调用 `ValleyAgentApi.TrySetAgentState`（或此分支直接回发 action_result，不经过 CommandExecutor）。
2. 新增 `set_state_failed` 的故障注入测试（对应测试篇 CH-01 海莉事件回归用例）。
3. 验证 `reason` 枚举：状态机拒绝映射到 `TransitionBlocked`，agent 未分配映射到 `AgentMissing`，非法状态名映射到 `InvalidState`。

### 2.5 与 TS 端的协议对齐（已落地）

C# 现在发 `action_result{success, reason}`，TS 端已消费 `reason` 字段并呈现给 LLM。实施细节：

### 4.1 P0 剩余：死管道决策（"接线或删除"政策）

**当前状态**：契约脚本已用 exit 1 钉死 8 个死管道。下一步必须逐个决策"接回 TS"还是"删 C# 发送端"。

**决策矩阵**：

| 死管道 | 推荐处置 | 理由 |
|---|---|---|
| `decision` | **删 C# 发送端** | Director 休眠（长期篇 §0.3：`grep "new Director"` 零匹配），定时 LLM 决策管线已死，NPC 现状靠 `RuleBasedDecisionEngine`。删发送端消除 60s 超时浪费，不改行为。删除位置：`EventHandlerInitializer.cs:1710-1713` 的 `_agentServerProvider.DecideAsync` 调用 + `WebSocketClient.cs:45` `DecideAsync`。 |
| `friendship_eval` | **并回 dialogue 主路径 + 删发送端**（见 §4.1.1 取舍） | `FriendshipSystem.cs:122` 调用卡 60s，catch 块（`:126-137`）不含 `TimeoutException` → 异常逃逸占住信号量 60s 串行化所有评估。采用方案 B（见 §4.1.1）：TS 在 `dialogue_response` 里带回 `friendshipDelta` 建议，C# 消费，既消灭死管道又保住 LLM 评估对话影响好感。 |

| `state_sync` | **删发送端** | `EventHandlerInitializer.cs:1255` 用 `SendTestMessageAsync` 卡 60s，catch 不含 `TimeoutException`。state_sync 的本意是推送状态让 TS 执行 `SetStateCommand`/`GiveGiftCommand`，但这些 Command 挂在死路径上（主设计 §0.4）。删发送端，相关 Command 代码一并清理。 |
| `rag_query` | **接回 TS 或删** | 需确认 TS 端是否有 RAG 查询能力。若 ValleyAI 无 RAG 服务，删；若有，在 `routeMessage` 加 case。 |

**执行顺序**：先删 5 个 wait-for-response 死管道（消除 60s 超时阻塞），再处理 3 个 fire-and-forget。每删一个，契约脚本对应的 DEAD_PIPELINES 项消失，逐步转绿。

**验证**：删 `decision` 后需启动游戏确认 NPC 行为不回归（应仍由 `RuleBasedDecisionEngine` 驱动，与删前一致）。

#### 4.1.1 friendship_eval 取舍：方案 A vs 方案 B

`friendship_eval` 死管道有两种消灭方式，**代价不对称，必须明确取舍**：

**方案 A：改本地评估**
- 做法：删 `_serverProvider.EvaluateFriendshipAsync`，`FriendshipSystem` 本地用 `EmotionAnalyzer` + 边际递减 + 生日倍率算 delta。
- **致命代价**：好感度只对**礼物**响应，不再对**说了什么**响应——"对话影响好感度"这条 P1 目标退化。`EmotionAnalyzer` 是规则引擎，无法理解对话内容的语义好感（如"夸赞/安慰/冒犯"），只能按礼物 taste 算分。Abigail 听到玩家说"你今天的紫色头发真好看"不会 +好感，收到紫水晶才 +好感。
- 适用前提：接受好感度退化为纯礼物驱动。

**方案 B：并回 dialogue 主路径**（采纳）
- 做法：TS 在 `runDialogue` 时让 LLM 同时评估好感变化，通过 `dialogue_response.friendshipDelta` 带回，C# 消费。删 `friendship_eval` 独立请求。
- 协议改动：
  1. TS `DialogueResponse`（`types.ts:33-42`）加 `friendshipDelta?: number` + `friendshipReason?: string` 字段
  2. TS `runDialogue` 的 LLM 调用加好感评估：system prompt 加规则"评估本轮对话对好感度的影响，输出 friendshipDelta（整数，可正可负可为零）"，用结构化输出字段或 `evaluate_friendship` 工具 call 承载
  3. TS `dialogue_response` 带回 delta + reason
  4. C# `dialogue` 响应解析加 `friendshipDelta` 字段
  5. C# `FriendshipSystem` 改为消费 `dialogue_response.friendshipDelta`（删 `EvaluateFriendshipAsync` 调用 `:122`）
  6. C# 删 `WebSocketClient.cs:63` `friendship_eval` 发送端
  7. 契约脚本 `friendship_eval` 从 DEAD_PIPELINES 消失
- 代价分析：
  - LLM 成本：每次对话多输出一个 friendshipDelta（微小增量，可并入现有响应结构）
  - 时序：dialogue 响应已回来，delta 在响应里，C# 直接应用。比原独立 friendship_eval 请求**少一次 WS 往返**，反而更快
  - 降级：LLM 不输出 delta 时默认 0（不阻塞对话），可加单测覆盖此路径
  - 测试：TS 单测验证 dialogue_response 带 delta；C# 单测验证消费逻辑；e2e 验证端到端
- 优势：保住"对话影响好感度"P1 目标，消灭死管道，减少一次 WS 往返，friendship 评估与对话语义同源（都是 LLM 理解对话内容）

**结论：采纳方案 B。** 理由：方案 A 的退化代价（对话不影响好感）直接违反 P1 目标，且不可逆；方案 B 的代价（LLM 微小增量 + 降级处理）可控可测。实施时机：TS 端 DialogueResponse 字段 + runDialogue 评估逻辑可单测先行，C# 端消费需游戏运行验证，归入下次会话。

## 7. 关键决策记录

### 7.1 为什么先做契约测试而非先删死管道

死管道删除是产品决策（接回 vs 删），有行为后果，需游戏验证。契约测试是**纯加法**（零风险），且立即把死管道钉成可观测的红色 backlog，防止后续 track 误把死管道当活路径依赖。先建守门人，再动代码。

### 7.2 为什么 action_result 只改 CommandExecutor 不改 DialogueBoxInputPatch

CommandExecutor 是纯逻辑（参数校验 + ItemRegistry 调用），可单测。DialogueBoxInputPatch 是 Harmony patch，驱动真实状态机，需游戏验证。本次守住"纯静态可验证"边界，避免交付不可测的改动。海莉事件的直接根因虽在 DialogueBoxInputPatch，但其修复依赖 CommandExecutor 的 Reason 枚举（本次已建），下次会话可直接消费。

### 7.3 为什么 prompt 重排要加段序断言测试

设计文档 §4.4 明确要求"防回归：加一个 TS 单元测试，对 DIALOGUE_SYSTEM_TEMPLATE 的段落顺序做断言"。没有断言，后人会把静态段又加到尾部（现状就是这样）。`indexOf` 单调递增断言是最低成本的防回归手段。

### 7.4 为什么 `{actual_state}` 段先留空占位

真实状态镜像由 `state_changed` 消息驱动（第 4.2 节），该通道未接入。若现在就填假数据会误导 LLM。条件注入（空则整段省略）保证当前不危害，接入后立即可用。这是为下次会话预留的结构插槽，不是占位符——填充逻辑是真实的条件判断。

### 7.5 ORPHAN_ROUTES 命名统一（已解决）

`tool_call_result` 原是 TS 路由但 C# 从不发（C# 用 `action_result`），命名分裂导致契约脚本持续报警告。已在反馈迭代中删除 `tool_call_result`（`types.ts` 删 `ToolCallResultMessage` 接口、`protocol-adapter.ts` 删 `handleToolCallResult` + `case "tool_call_result"`、`messages.json` 删条目、5 处测试改用 `action_result`），两端统一用 `action_result`。ORPHAN_ROUTES 现为 0。保留 ORPHAN_ROUTES 警告机制防未来再出现 orphan。
